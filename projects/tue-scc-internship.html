🖥️ Supercomputing Robotics: Isaac Sim across TU/e's HPC Platforms

February 2026 - June 2026 (20-week work placement · Hybrid, Eindhoven)

Company: TU/e Supercomputing Centre (SCC) - AI Team, Eindhoven University of Technology

Supervisors: Nick Brummans (AI Team lead, function supervisor) · Richard Zoontjens (SCC lead, company supervisor)

Role: AI & HPC Research Engineer (Intern) - Isaac Sim Benchmarking, Deployment & Researcher Support

Internship Overview

For my third-year work placement I joined the AI Team of the TU/e Supercomputing Centre. The SCC does not own one big supercomputer; its job is to help researchers reach the right compute for their problem, under the motto "Compute to Compete." I arrived just as the centre was learning to use its newest hardware: SPIKE-1, four NVIDIA DGX B200 systems (eight Blackwell GPUs each, hosted in a data centre in Finland), alongside a desktop-class DGX Spark.

The question I ended up answering sounds simple: which platform fits which robotics-simulation workload, and how do we get researchers running on it independently? Over five months that turned into three interlocking strands: cross-platform benchmarking of NVIDIA Isaac Sim and Isaac Lab, a containerised Isaac Sim deployment on SPIKE-1, and hands-on support for two research teams. A communication layer of presentations and documentation tied it all together.

The Challenge

The SCC had invested heavily in Blackwell hardware, but nobody had yet characterised how it behaved for robotics simulation, a workload more and more TU/e researchers were asking for. Three concrete problems followed:

• No evidence for platform choice: researchers had to choose between the DGX Spark, SPIKE-1, SURF Research Cloud and Snellius without any benchmarks to go on
• No reproducible deployment: there was no way to run Isaac Sim on SPIKE-1's containerised, Run:AI-orchestrated environment, so every researcher would have to reinvent the wheel
• GPU physics appeared broken: during physics simulation the Blackwell GPUs sat at 0-3% utilisation, which, if true, would block all GPU-accelerated reinforcement learning on the centre's newest hardware
• Shadow IT: some departments were considering buying their own DGX Sparks; the SCC wanted to show it could provide and support this capability centrally

My Approach

I chose an empirical, documentation-first approach: build one reproducible benchmark, run it identically on every platform, and write honest, self-contained documentation per platform, including the failures.

1. Isolate Variables: Separate physics from rendering, headless from GUI, and CPU from GPU execution, so every measured difference has a single cause
2. One Repository per Platform: Each platform got its own self-contained repo (README, user guide, numbered setup guides, benchmark JSONs and plots) that works on its own
3. Document the Dead Ends: When a platform proved unworkable, I documented why instead of quietly dropping it, a failed platform written down saves the next person weeks
4. No Sales Pitch: Presentations drew conclusions from the data and positioned HPC as one option among several, rather than promoting SPIKE-1 regardless of fit
5. Platform as a Workshop: Instead of running researchers' jobs for them, build an iteration loop they can use without the SCC in the way

Benchmark Design

Early on I learned that render=True versus render=False changes everything: with rendering on, even headless, the GPU lights up, but that activity is rendering, not physics. I built separate modes (--mode physics / render / combined) and consolidated the suite into seven reproducible categories, each run headless on every platform and exported as JSON plus plots.

Seven Benchmark Categories

1. Rendering throughput (ray-traced warehouse scene)
2. Physics on CPU (articulated robots, render off)
3. Physics on GPU (up to 10,000 rigid bodies)
4. Combined real-world workload (physics + rendering)
5. Isaac Lab RL environment stepping (Cartpole, G1 humanoid, Shadow hand, ANYmal-D)
6. GUI versus headless overhead
7. Scene loading

Case Study: "Broken" GPU Physics on Blackwell

The most important result of the internship started with an alarming symptom. On both the DGX Spark (GB10) and SPIKE-1 (B200), across Isaac Sim 5.0.0, 5.1.0 and 6.0.0-dev, GPU utilisation sat at 0-3% during physics while rendering used the GPU normally. The clearest signal: all three physics backends gave identical, CPU-only numbers.

The Symptom

Backend: GB10 / B200
warp (GPU): 31.4 / 26.0 FPS
torch: 31.4 / 26.1 FPS
numpy (CPU): 31.3 / 27.0 FPS
Identical numbers = everything
was silently running on the CPU

The Investigation

• Built a physics-only benchmark, which exposed my own earlier false positive (94% GPU utilisation was rendering, not physics)
• Reproduced on two GPU models and two CPU architectures (ARM Grace, x86 Xeon)
• Escalated through the NVIDIA Developer Forums and an NVIDIA Enterprise Support case, working with an L3 support engineer
• Publicly corrected my wrong conclusion on the forum instead of quietly editing it

Root cause: Isaac Sim's World() does not enable GPU dynamics by default. The settings that report "GPU physics enabled" are only hints; the PhysX SDK reads attributes on the USD physics-scene prim and silently falls back to the CPU when they are missing. Documented behaviour, not a driver bug, so no driver downgrade was needed (which matters, because the GB10 will not boot on older drivers). 


# The fix: set GPU dynamics explicitly on the physics scene prim
from pxr import PhysxSchema

my_world = World(
    stage_units_in_meters=1.0,
    physics_dt=1.0 / 60.0,
    physics_prim_path="/World/PhysicsScene",
)

physx_scene = PhysxSchema.PhysxSceneAPI.Apply(
    my_world.stage.GetPrimAtPath("/World/PhysicsScene")
)
physx_scene.CreateEnableGPUDynamicsAttr().Set(True)
physx_scene.CreateBroadphaseTypeAttr().Set("GPU")

# Validated two independent ways (10,000 rigid cubes):
# SPIKE-1 (B200):   214.7 FPS CPU  ->  376.0 FPS GPU   (+75%, 1.75x)
# DGX Spark (GB10): 353 FPS CPU    ->  542 FPS GPU     (+53%)

The scaling result was the second surprise: at 10,000 bodies the GB10 beat the far larger B200. Unified memory lets the Spark share physics data between CPU and GPU without copying it across PCIe every step, which gives it a structural edge for small-to-medium physics.

Read the public thread: PhysX GPU not working on DGX Spark (GB10 Blackwell, ARM64), NVIDIA Developer Forums

Containerised Deployment on SPIKE-1

To make Isaac Sim usable on SPIKE-1 I built a cross-architecture container pipeline. The DGX Spark is ARM64 and SPIKE-1 is x86_64, so images are cross-compiled with Docker buildx, pushed to the TU/e Harbor registry, and launched as Run:AI workloads. Four variants cover the realistic use cases:

Deployment Pipeline

Code locally → Docker build (linux/amd64) → Harbor registry → Run:AI submit → SPIKE-1 B200s (train + log to W&B)
• IsaacSim-VNC - Isaac Sim with TurboVNC for interactive GUI work
• IsaacSim-noVNC - headless Isaac Sim for clean throughput
• IsaacSim-IsaacLab-VNC - adds Isaac Lab, with GUI
• IsaacSim-IsaacLab-noVNC - adds Isaac Lab, headless

For researchers I adopted one deliberate rule: the container provides only the environment (CUDA, drivers, uv, system libraries) and the researcher's code is cloned fresh into a workspace on every run. Editing happens in VS Code over SSH, and code changes never need an image rebuild. That is what turned SPIKE-1 from a job-submission service into a fast iteration loop.

Along the way I characterised the platform limits too: WebRTC streaming is not possible under the current Run:AI setup (the port-forward is TCP-only, WebRTC needs UDP), which is why TurboVNC is the supported route, and the Isaac Sim GUI crashes above 32K environments on a buffer-aliasing assertion that is distinct from genuine out-of-memory failures.

What Went Wrong (and How I Fixed It)

DGX Spark: a routine sudo apt upgrade bricked the machine with a kernel panic (VFS: Unable to mount root fs). I recovered it through the GRUB recovery menu and a USB flash drive, and the lesson made it into the setup guide in bold.
SURF Research Cloud: the default 595 driver caused segfaults, so step one of every setup is now purging it and installing the 580 series. Installing ros-humble-desktop destroys the remote-desktop session, so the guide avoids it.
Snellius: all four Isaac Sim test jobs failed (a PhysX GPU memory error, a fatal H100 crash after 88 ms, and toolchain incompatibilities). Fixing it would need a driver downgrade that is not possible on a national system, so I documented it as an honest dead end with root-cause analysis.
Version pinning: Isaac Lab's main branch is incompatible with Isaac Sim 5.1.0, so every guide pins Isaac Lab v2.3.2.

Key Learnings

Test to Find Out: Published benchmarks assume a mature software stack. Blackwell plus Isaac Sim was new enough that documented and real behaviour diverged, which is exactly why first-hand experiments had value.

Being Correct Beats Being First: My first PhysX conclusion was wrong and I had to correct it publicly. Isolating subsystems and validating the fix two independent ways is what produced an answer people could trust.

Always Document Everything, Including Failures: The Snellius dead end and the bricked Spark are now pages in a guide instead of traps for the next person.

Talk to Colleagues: The breakthroughs came from people: NVIDIA's support engineers, SURF support, and a team that reviewed my benchmarks for rigour. Knowing when to stop debugging alone and bring in the right person is a skill.

Scope to Finish: My recurring feedback was to focus and not try to do everything. Learning to let a good idea go and head for the finish line was one of the most useful things I took away.
